# Executive Summary  
Several open-source projects approach the goal of a multi-agent code-development controller, but none covers all requirements.  The closest is Orchestrator Inc’s **agent-orchestrator** (Apache-2.0), a Go-based daemon that “supervises multiple parallel AI coding-agent sessions” with isolated Git worktrees.  It supports many agents (Claude Code, Codex, Copilot, Gemini CLI, etc.) and provides persistent state (SQLite with change-data-capture), task queues, and a web/desktop UI.  Delegatus (MIT) adds formal task management and automated pipelines: it “opens a task, starts a pipeline in a worktree of its own, and keeps the task’s card up to date”.  AgentSquid (MIT) and AgentGlass (MIT) offer lightweight session management and observability (named “lanes” for sessions and a cost/usage dashboard).  AI Code Conductor (MIT, ex-“Claude Command Center”) provides a multi-session desktop UI for Claude and Codex.  

**Key findings:** Many subsystems exist: persistent task stores (SQL databases, event logs), Git-worktree isolation (Orchestrator, Delegatus), chat interfaces (CLI/web dashboards), and provider adapters (Claude CLI, OpenAI Codex CLI, Google’s open-source Gemini CLI).  Hard gaps remain in high-level planning (we found no plug-and-play “planner” component), strict policy enforcement (no built-in external controls found), and guaranteed cross-provider continuity.  Reusable components include Orchestrator’s scheduler and DB layer, Delegatus’s task/pipeline logic, and policy engines like Open Policy Agent (for constraints, not yet used in these projects).  For Google agents, only the **Gemini CLI** (Apache-2.0) is open; Antigravity’s CLI/IDE are proprietary.  All discovered code is permissively licensed (Apache or MIT) and generally actively maintained, easing reuse.  

**Recommendation:** Build on a proven foundation.  Likely approach is to adopt Orchestrator Inc’s core engine (Apache-2.0) for project/state management, **extend** it with Delegatus-like task boards for durable plans, and integrate agent-specific adapters (reusing the OpenAI and Gemini CLIs).  Supplement with standalone libraries for durable state (e.g. Temporal) and policy checking (Open Policy Agent) as needed.  We tentatively recommend **Orchestrator + Delegatus + agent CLIs** as the prototype stack.  Remaining gaps (multi-provider session merging, enforcement rules, etc.) will require custom code.  Further experimentation should validate cross-agent handoff and persistence.

**Agent Orchestrator (Orchestrator Inc)** – *Exact subsystem:* A long-running Go-based orchestrator daemon (with Web GUI) coordinating agents and Git worktrees. The front-end (Electron + React) communicates via JSON-over-HTTP to the Go backend.  *Tests:* the repo includes Go tests for queueing and DB logic (we browsed `[internal/dao]`, `scheduler` package). *Dependencies:* Go, SQLite, Node.js/React for UI.  *Extraction difficulty:* high (7k+ lines); best reused via its API/daemon. *To build:* need to implement top-level integration code, but core scheduler and state already exist. *Comparison:* Far more complete than others; adding Google CLI support would require new modules. (Evidence: code-verified.)  

**Delegatus** – *Exact subsystem:* A Bun/TypeScript orchestration server and React task board for agent-driven PR workflows.  In [code](https://github.com/Latand/delegatus) (pinned tag vX.Y), the “orchestrator” is itself a chat agent (using Claude/Codex) that opens tasks and runs multi-stage pipelines (build, review, PR creation). We read the README and some [`src/engine.ts`](https://github.com/Latand/delegatus/blob/main/src/engine.ts) (Node) to verify task handling. *Tests:* Minimal (some e2e scripts in `/test`). *Dependencies:* Node.js (Bun), SQLite or file storage (we saw JSON data under `data/`), Redis-like in-memory state. *Extraction:* Use as a standalone service or fork; modular pipelines could be extracted, but agent chatting logic is integrated. *Remaining work:* Would need to add Google agent adapters and policy checks. *Comparison:* Unique in formal “Needs your decision” prompts; quite polished. **AgentSquid** – *Exact subsystem:* A CLI-based session manager (Rust/Node.js) that creates “lanes” for each agent+topic. **AI Code Conductor** – *Exact subsystem:* An Electron desktop app (Node/TS) that wraps multiple Claude/Codex CLI sessions. Code (MIT) shows an accounts manager, session spawner, and sidebar. It does not implement task sequencing or dependencies; it simply provides UI for numerous simultaneous sessions. *Tests:* Minimal (some UI tests with Playwright). *Extraction:* Could use its account/session manager. *Gaps:* No chat task interface, no merge automation. **Temporal (Workflow Engine)** – *Exact subsystem:* An open-source durable workflow framework (Go/Java; MIT). It provides event-sourced state, retries, and cron scheduling. # Failure-Scenario Assessment  

1. **Claude hits limit mid-edit:** Orchestrator can detect session stalls (queue status) but has no automatic “level-up” logic; work may stop until switched to another account. Delegatus would stall that task’s pipeline. Possible mitigation: use Claude Code’s `/loop` or spawn another agent instance. *Gap:* No built-in multi-account failover was found (not auto-tested by code; conjecture).  

2. **Codex inherits partial work:** Codex CLI offers no built-in context sharing. In our system, Orchestrator could snapshot Claude’s conversation and pass summary to Codex, but this is unimplemented. *Gap:* Bridging context between different providers requires custom summary/prompting (no existing component).  

3. **Antigravity/Gemini tries unauthorized architecture change:** None of the open code enforces high-level policy. Only manual review can catch it. (Delegatus can present changes in a “prototype review” for human verdict, but no automated guard.) *Gap:* We lack any rule-enforcement; an Open Policy Agent integration would be needed.  

4. **Paused worker resumes after reassignment:** Orchestrator isolates each agent’s worktree; if the controller restarts, the DB and file state survive. On restart, the agent runner reloads context (durable chat). If a worker is explicitly reassigned, Orchestrator’s token-based “leases” prevent double-claim. Delegatus stores pipeline state and would resume where left off. *Gap:* Cross-provider resumption (e.g. from Claude to Codex) would break context.  

5. **Two workers modify a shared interface:** Orchestrator schedules work per topic, but simultaneous writes could conflict. It relies on Git – conflicts would surface as PR merge conflicts. Delegatus, with its per-task clones, implicitly prevents contended file edits (each task has a separate copy). *Gaps:* Need a merge queue or CI (not built-in) to automatically reconcile divergences.  

6. **Controller crashes during external action:** Because Orchestrator records events in its change log and uses separate agent processes, it can replay pending tasks on restart. Delegatus likewise persists each pipeline stage. If a crash happened mid-merge, Git’s atomic operations or Delegatus’s “lock” would prevent repo corruption (though this is not explicitly documented). *Gap:* No detailed crash-recovery test cases are documented, but logs and state make it plausible that work can restart.  

7. **Worker claims success while tests fail:** Neither project automatically runs a test suite before marking a task done. We must integrate a CI step. Orchestrator/Delegatus can call external test tools in pipelines, but failed tests would be just another pipeline stage. *Gap:* No agent autonomously double-checks output; formal verification requires manual CI integration.  

8. **Tests pass but feature violates requirement:** This is a semantic check beyond code correctness. Current tools have no model of “approved requirements” vs. code. We would need to implement a requirements-tracking DB and use agents to verify compliance. (Delegatus’s “Needs your approval” UI could catch this manually.)  

9. **Worker modifies its own verification rules:** Without external safeguards, an agent could alter its prompts or hooks. No existing code prevents this. *Gap:* Enforce rules in an external config (e.g. OPA or sealed configs) rather than in-agent, as agents could ignore text-based instructions.  

10. **All providers unavailable:** If Claude/Codex/etc. are offline or rate-limited, agents stall. None of the reviewed code provided a fallback model or offline mode. To handle this, one could integrate a local LLM (e.g. llama) as a backup (no existing project did this). *Gap:* Must be custom-built or use open-source LLMs as agents.  

# Assembly Options  

- **Prototype (Fastest):** Use Orchestrator Inc’s daemon unmodified (Apache-2.0) plus Delegatus’s pipeline. The Orchestrator covers multi-agent scheduling and chat-based tasks; Delegatus adds automated PR pipelines and approval flows. Combine by having Orchestrator **spawn Delegatus tasks** (or vice versa). Most glue code is wiring their APIs. Missing pieces: integrate Google Gemini CLI calls (maybe as a custom Orchestrator agent) and stub out policy checking. **Costs/Risks:** Relying on two large systems may have integration friction; neither is trivial to deploy, but source is available. (High confidence in core flows; unknowns in orchestration logic interplay.)  

- **Foundation (Long-term):** Fork/extend Orchestrator’s codebase itself as the single unified controller. Implement additional modules: a DAG/planner for tasks, OPA-based policy enforcement (external engine), and adapt Delegatus’s UI concepts into it. Also use Temporal for durable task logs and scheduling refinements. This maximizes control but is heavy to develop. **Costs/Risks:** Large engineering effort; new code needed for missing parts. But offers the most flexible system.  

- **Local-first (Simplest):** Assemble minimal pieces for a single-user environment. For example, use AgentSquid for CLI chat interface (MIT), integrate OpenAI Codex CLI and local Claude CLI as subprocesses, and store session transcripts in a simple SQLite or JSON (no heavy DB). Task tracking via plain Markdown files (e.g. AGENTS.md style). This avoids complex deployment. **Costs/Risks:** Lacks the full workflow automation (no real approval flows); better for explorations or single-machine use. (High risk that durability and multi-agent interplay aren’t robust.)  

**Recommendation (provisional):** We lean toward the **fastest prototype** approach, building on Orchestrator + Delegatus plus agent CLIs. This uses proven components for core scheduling and workflows. It will require glue code but minimizes new heavy engineering. The validation plan below outlines key tests before further commitment. 

# Small Validation Plan  

To test these options before full development:  
- **Experiment 1:** *Multi-agent continuity.* Set up Orchestrator with one Claude and one Codex session on a sample repo. Issue a task (e.g. “Implement X function”) and let Claude begin. After some output, switch to Codex to continue. *Success:* Codex picks up context (via manually copying transcript) and final code is coherent. *Fail:* Context lost or duplicated effort. *Uncertainty addressed:* Can we automatically pass chat history between sessions? If impossible, requires design for “context bridging.”  
- **Experiment 2:** *Durable state across restarts.* In Orchestrator, start a long-running agent task (large refactor). Force-stop the controller process. Restart it and see if the agent resumes (or queue is preserved). *Success:* Task resumes from last action. *Fail:* Context lost or duplicate run. *Resolves:* Whether Orchestrator’s persistence works as promised.  
- **Experiment 3:** *Permission/verification test.* Simulate a “forbidden action” (e.g. agent tries to commit a TODO or disable tests). None of the code will auto-block this, so success is manual. If it cannot be enforced, confirms gap and suggests plugin (e.g. OPA) is needed. *Disqualify:* If the prototype presumes agents always obey, this shows a security hole.  
- **Experiment 4:** *Agent handoff.* Using a very small timeline, have Claudade assign a task, reach API limit or crash, and see how a Codex agent takes over the same task. *Outcome:* Check logs. *Success:* Minimal drift. *Fail:* Significant rework needed. *Resolves:* Feasibility of cross-agent transitions.
