# Source-Code Reuse Audit for an Authoritative Cross-Agent Development Controller

## Findings and recommendation

### Bottom line

No inspected project currently delivers the whole target: a **persistent, authoritative project controller with central chat, durable approved decisions, cross-provider worker replacement, mechanically enforced task ownership, independent verification, and first-class Claude Code + Codex + Antigravity support**. The strongest existing systems divide into two camps: polished agent/session runners that are weak on authority, and authority/workflow tools that are weaker on chat, provider integration, or production maturity. citeturn971197search2turn971197search0turn971197search1turn530342search1

The closest **runtime/UI foundation** I found is [OrchestratorInc/agent-orchestrator](https://github.com/OrchestratorInc/agent-orchestrator), pinned for this audit at [`fe0550a`](https://github.com/OrchestratorInc/agent-orchestrator/tree/fe0550a). Its architecture already separates a long-running daemon from the Electron/React UI, persists session state in SQLite, owns project worktrees, has provider-specific Chat drivers, survives daemon replacement through detached provider hosts, and implements a real controller-generation fence plus durable outbox around interface handoff. It also explicitly distinguishes provider-native resumption from cross-provider continuation: Claude Code and Codex can retain the *same native conversation* only where AO has proved equivalent native IDs; a provider change does not imply inherited context. citeturn352229view0turn971197search2turn971197search3

The closest **authority and acceptance implementation** I found is [agent-sh/tower-crane](https://github.com/agent-sh/tower-crane), for which the latest published release visible during research was `0.1.7`. Tower Crane has task dependencies, decisions, evidence, leases, budget/spend records, independent review, software gates, accepted-commit pinning, worktrees, stacks, a merge queue, and a state broker intended to prevent sandboxed Claude/Codex workers from directly mutating authoritative state. It is unusually aligned with the requirement that *workers submit results; they do not decide for themselves that the task is complete*. Its current weak point for this project is important: Antigravity is supported as a harness, but Tower Crane itself says native enforcement and message delivery for Antigravity are still future work. citeturn971197search0turn530342search0

The best **small ownership primitive** is [DmarshalTU/coord](https://github.com/DmarshalTU/coord), pinned at [`44fe390`](https://github.com/DmarshalTU/coord/tree/44fe390). It provides a local SQLite/WAL coordinator with atomic claims, leases, expiry/reclaim, transactional complete-plus-ack, long-poll observation and multi-process race tests. It is much smaller than an agent platform and is therefore attractive as a source of scheduling semantics. Its documented claim model is not, however, sufficient evidence of an external-side-effect fencing token that prevents a stale process from writing a branch after its lease has been stolen. citeturn352229view3turn530342search1

The strongest explicit **fencing-token design** I found is the git-native backend in [tasksmd/tasks.md](https://github.com/tasksmd/tasks.md). Its `claim_id` is explicitly a fencing token; task commits carry the claim ID, and stale owners cannot complete or release a task after a later owner has stolen the expired lease. Claims use Git ref compare-and-swap, and the event fold is deterministic and idempotent. This solves a narrower problem very well, although it uses a dedicated Git ref/event log rather than the structured controller database you are asking for. citeturn375168search6turn678672search0

For **provider adapters**, the best long-term choice is not to standardize on terminal scraping. Current first-party interfaces are substantially better:

- Claude Code exposes noninteractive `-p`, `stream-json` input/output, explicit session resume/continue, tool allow/deny lists, permission modes, bounded turns, and a noninteractive permission-prompt tool. Claude Code also supports Claude App Pro/Max login as an officially documented authentication path. citeturn718889search6turn718889search7
- Codex now exposes a documented **app-server** harness interface intended for product embedding: persistent threads, streamed events, interrupts, approvals and tool execution. OpenAI explicitly positions `codex exec` for bounded jobs, the SDK for ordinary programmatic workflows, and app-server for applications that need lifecycle control. citeturn375168search4
- Antigravity CLI has a real headless protocol through `agy`: `stream-json`, cached-account authentication, explicit conversation continuation, permission policy, model/agent selection and machine-readable lifecycle states. It is distinct from Gemini CLI even though the products share heritage and infrastructure. citeturn718889search0turn718889search1

The key architectural conclusion is therefore **composition, but not naïve process-level composition of multiple competing control planes**. The most justified path is to **extend a mature session/runtime foundation—currently OrchestratorInc/agent-orchestrator—and add one authoritative task/decision/acceptance state machine borrowing proven semantics from Tower Crane, coord and tasks.md**. Provider execution should progressively move to native structured interfaces: Codex app-server, `agy` headless streaming, and a Claude Code structured interface that is validated against the exact subscription/billing behavior you intend to preserve. This avoids making Codex, Claude or Gemini the irreplaceable manager. citeturn971197search2turn971197search0turn530342search1turn375168search6

I would **not** start by forking Agetor as the long-term foundation, despite its unusually good three-agent coverage. Agetor is excellent evidence that one UI can drive Claude Code, Codex and Antigravity with existing CLI logins, but its Claude integration deliberately uses an interactive tmux session and transcript tailing, with live question detection scraped from the terminal pane; it is a useful prototype and adapter reference, not the authority boundary I would want to depend on. citeturn971197search1turn971197search4

### Evidence grading used in this report

There is **no Executed evidence** in this audit. I did not install or run any of these projects or use account credentials. Repository cloning from the available execution environment was unavailable, so code inspection was performed through GitHub source/diff pages, repository documentation, tests exposed in repository pages, release pages, issue reports, and current first-party product documentation. Where I saw implementation code or source diffs, I label the finding **Code-verified**. Where repository tests were inspected or specifically documented but not run, I use **Test-supported**. Maintainer claims not independently traced into source are **Documented only**.

This distinction matters particularly for Tower Crane and Agetor: both have unusually detailed maintainer documentation, but not every claimed behavior below was followed all the way into the implementation during this pass.

## Deep source audits

**OrchestratorInc/agent-orchestrator — strongest runtime/session substrate.** The current architecture is more sophisticated than its “multi-agent desktop app” description suggests. The durable store is SQLite with goose migrations and sqlc-generated queries; database triggers populate a `change_log`, and a CDC poller feeds in-process subscribers and SSE clients, including replay using `Last-Event-ID`. Session lifecycle logic is split across `backend/internal/session_manager`, lifecycle/reaper code, SCM observers, agent adapters and workspace adapters. This is exactly the separation needed if chat, scheduling and execution are not to collapse into one model loop. citeturn971197search3

The particularly reusable mechanism is **session controller replacement**. In `docs/architecture.md`, AO describes one committed controller per session, a persisted controller generation, a runtime launch ID for TUI hooks, a durable message outbox during no-controller windows, and CAS rollback if the target controller fails during handoff. Old Chat events are rejected by generation; old TUI hooks are fenced by runtime launch ID. If the daemon dies during the transition, startup reconciliation restores the controller indicated by the last committed session mode. That is real crash/replacement engineering rather than a prompt handoff. **Evidence: Code-verified architecture and status; Test-supported, not executed.** citeturn971197search2turn971197search3

AO is also commendably explicit about what it **does not** prove. An interface handoff preserves a provider-native conversation only when the source and target IDs have been shown to refer to that same native conversation; currently Claude Code and Codex satisfy that contract for the supported interface transition. Persisted AO history from a different provider is not represented as native context inherited by the new provider. That is the correct conceptual boundary for your project: cross-provider continuation must be based on authoritative task/project state and workspace evidence, not pretending a Claude conversation ID can become a Codex or Antigravity session. citeturn971197search2

The weakness is that AO's durable object is fundamentally a **session**, not an externally authoritative task specification with immutable approved acceptance criteria. It already has enough durable machinery to host such a layer, but it does not by itself give the semantics “proposal → approved decision → observed fact” or “worker submitted → controller independently accepted.” That remains for us.

Its failure record is also instructive. Inspected open issues describe non-atomic windows around worktree creation, recovery states that can make archive/kill operations behave incorrectly, failed switching that can retain a durable switch lock, native-history resume failures, and long-lived Codex app-server instances retaining stale authentication state after account changes. Those are not reasons to reject it; they are evidence that session lifecycle is a difficult subsystem and that AO is already encountering the right class of production failures. The takeaway is to reuse its lifecycle machinery but not assume it is infallible.

From a licensing perspective, the repository is Apache-2.0, a good fit for an open-source derivative or extracted code, subject to preserving the license/NOTICE requirements where applicable and respecting the Apache patent terms. Dependencies need their own SBOM review; an Apache root license does not convert third-party dependencies to Apache. citeturn267120search4

**Preferred reuse:** fork/extend the foundation or contribute an authoritative task subsystem upstream if project direction permits. A pure “depend on package” approach is less attractive because much of the useful behavior is internal daemon architecture rather than a small stable library.

**Agetor — best current demonstration that all three target CLIs can coexist behind one local control plane.** Agetor's architecture is clean at a high level: a Bun core owns orchestration, SQLite and Git; React/Electrobun and the CLI communicate with the core through loopback HTTP and SSE; a worktree is created per task. Tasks, runs, events, projects, harnesses and preferences are persisted with migrations, and on restart the controller reattaches to still-running tmux sessions or marks missing ones orphaned/ready instead of leaving cards permanently “running.” citeturn971197search1

Its `src/bun/agents.ts` is documented as the central dispatch point: `buildCommand(...)` constructs agent invocation, and `spawnAgent(...)` routes to per-agent drivers such as `claude-tmux.ts`, `codex-tmux.ts` and ACP drivers. Adding a harness requires extending `AgentKind`, migrations, binary resolution/environment/command generation, availability discovery and the follow-up/restart path. This is a useful concrete adapter pattern. citeturn971197search1turn971197search4

Agetor distinguishes our three relevant products correctly. Claude Code is an **interactive `claude` process** in a per-task tmux session. Codex is invoked as `codex exec --json`, one bounded turn at a time, and continues via thread ID. Antigravity is the `agy` binary in `stream-json` headless mode, continuing by conversation ID. Gemini CLI is a separate harness entry using the `gemini` binary and its own session ID. That is exactly the distinction the requested audit needed to preserve. citeturn971197search1

The implementation also reveals why terminal-driving is not ideal as the permanent interface. For Claude's `AskUserQuestion`, Agetor reports that it first probes the JSONL transcript but currently has to scrape the tmux pane while the modal is open because the relevant tool-use event is not written to the transcript until after an answer in the Claude versions its maintainers tested. Prompts themselves are sent as tmux keystrokes. On macOS Agetor includes a signed helper using a private responsibility-related spawn facility to address TCC attribution for spawned tools. Those are clever engineering accommodations, but they increase OS/version coupling and extraction cost. citeturn971197search4

Agetor also documents a claim that it deliberately uses Claude interactive mode rather than `claude -p` to preserve a particular subscription-credit path. I did not find an equally specific current Anthropic primary-source statement that confirms Agetor's precise June-2026 billing distinction, so that particular claim should be treated as **unverified outside Agetor** until reproduced against your intended account type. Anthropic does officially state that Claude Code supports Claude App Pro/Max login, while its CLI docs describe `-p` as programmatic/SDK mode. citeturn971197search4turn718889search6turn718889search7

**Preferred reuse:** fork for a quick prototype or use its adapters as design/source references. I would not make its tmux/transcript conventions the permanent provider abstraction unless the billing experiment proves there is no supported structured alternative compatible with your subscription.

**Tower Crane — strongest inspected model of external authority.** Tower Crane's state model is unusually close to your requirements: `.tower-crane/project.json` stores project settings and ladder, `tasks.json` stores tasks/evidence/spend, `decisions.json` stores owner questions, `briefs/` stores task context, and `events.jsonl` records changes. A task becomes ready only when dependencies are accepted and no blocking decision remains. Claims are leases renewed while work progresses; expired leases release work. citeturn971197search0

Acceptance is controller-owned. `accept` runs software gates, records command receipts as evidence, and then dispatches an independent reviewer whose context contains the diff, acceptance criteria and gate results. A failed review can send the task into rework. Tower Crane's stated merge semantics require an accepted task and pin merge evidence to the accepted head. This is far closer to “completion is a state transition authorized by acceptance” than the usual agent pattern of trusting a final natural-language message. citeturn971197search0

Its sandbox/state-broker concept is also relevant. Tower Crane states that Claude Code and Codex can run with isolated homes, sandboxes and a brokered command surface so workers do not directly edit authoritative controller state. The same repository explicitly states that **native enforcement for Antigravity remains unfinished**, which is exactly the kind of negative evidence this audit should surface. citeturn530342search0

Testing evidence is better than average for a young tool. The maintainers describe integration tests that invoke the actual Tower Crane CLI against temporary Git repositories and specifically point to claim tests; the CLI itself has no npm dependencies. I did not run those tests, so this is **Test-supported, not Executed**. The version is only `0.1.7`, and the project itself is young enough that production confidence should remain lower than its feature breadth suggests. citeturn530342search0

The internal state format is also a tradeoff. Plain JSON + append-only event log is transparent and local-first, but if Tower Crane is embedded beside AO's SQLite store, two authoritative state systems would create synchronization and crash-consistency problems. Reusing the **gating, broker and task-lifecycle mechanisms** is more attractive than running Tower Crane and AO as equal competing sources of truth.

**Preferred reuse:** integrate through its CLI only for an initial experiment, or vendor/extract bounded authority/gating logic after a deeper module-level license/dependency audit. Long term, preserve its semantics inside one controller-owned transactional database rather than dual-writing Tower Crane JSON and AO SQLite.

**coord — focused scheduling code that is small enough to reason about.** `coord` has the useful property of doing far less. Its core concern is task ownership and communication, with SQLite/WAL underneath and interfaces over JSON-RPC, a subset of A2A, and MCP. The documented atomic claim is a conditional SQL update on a pending task; only one concurrent claimant gets the row. Claims have leases, the owner can renew, and expiry returns work for reclaim. Version `0.4.1` added atomic completion plus acknowledgement in the same transaction. citeturn530342search1turn352229view3

The repository claims eleven end-to-end tests gating changes, including a 16-process claim race, a lease/auto-reclaim cycle, long-poll wakeup and protocol-level multi-client behavior. Its current commit diff exposes test and core-store paths, so the existence of the test machinery is **Code-verified/Test-supported**, but none was run here. citeturn530342search1turn352229view3

What `coord` does **not** obviously provide is just as important. A lease tells the scheduler who owns the task now. Unless every externally meaningful effect—commit acceptance, branch update, merge, authoritative state mutation—also carries a monotonically current fencing token, a stale process can still perform side effects after its lease expires. `coord` is therefore a good scheduler primitive, but its lease semantics should be augmented with an explicit generation/claim token at the controller boundaries.

**Preferred reuse:** integrate as a subprocess/service through its JSON-RPC surface only if having a separate ownership database is acceptable; otherwise use its store/tests as design reference and reproduce the transaction pattern in the primary controller DB.

**tasks.md git-native backend — best explicit stale-worker fencing semantics.** The collision-free backend makes the fencing property first-class. A successful claimant mints `claim_id`; work commits carry `Task` and `Task-Claim` trailers; heartbeat, release and completion are checked against the live claim. After expiration, another agent can steal with a new `claim_id`, and the old owner can no longer successfully finish the task. Git's non-fast-forward rejection is the compare-and-swap primitive for claim races. citeturn375168search6

This is stronger than merely marking a lease expired because it gives us an identifier that can be required at every later submission/acceptance boundary. However, it still does not magically stop the old OS process from modifying files in an already writable worktree. A fencing token prevents the controller from *accepting* stale work; preventing further writes requires terminating/revoking the stale worker's workspace or ensuring each ownership generation uses a separately controlled workspace.

Its MIT license was inspected directly. citeturn662411view1

**Preferred reuse:** design reference for claim-generation/fencing; possibly depend on its parser/spec if we want TASKS.md interoperability, but do not make Markdown the authoritative project state.

**AWO — best small deterministic verification/proof-pack reference.** AWO deliberately trusts configured command exit codes rather than an agent's assertion of success. It runs Claude Code or Codex in isolated worktrees and writes durable artifacts including `run.json`, a proof pack, patch, and stdout/stderr. Writer-reviewer mode gives the reviewer a separate read-only worktree and treats reviewer edits as an anomaly. It deliberately does not commit, push, merge or open PRs. citeturn588570search0

That narrow scope is valuable. The proof-pack concept is suitable for our acceptance layer: every submission should retain the exact target commit, diff, commands, exit results, relevant logs and provider metadata even after the worker disappears. But AWO is not a scheduler: its roadmap says rerun/resumption and more backends are future work, and `maxIterations` is currently fixed at one. Antigravity is not supported. citeturn588570search1

Its pinned license is MIT and was directly inspected. citeturn662411view0

**Preferred reuse:** extract or independently reproduce the bounded proof/verification layer; do not use it as the controller.

**AWS Labs CLI Agent Orchestrator — good separation, wrong enforcement defaults for this project.** CAO's architecture separates FastAPI routes, services, terminal backends and provider adapters, which is a useful structural precedent. It has local sessions, terminal/worktree management, inbox/event functionality and durable script-tier workflows in recent releases. The current release stream reached `v2.5.3`; the current main source inspected here was at `261c5e1`. citeturn530342search3turn216060view1

Its Antigravity integration, however, has relied on an interactive TUI and terminal-state observation rather than Google's current `agy` headless event protocol, and the inspected Claude provider has code paths using `--dangerously-skip-permissions`. Those choices make it a less suitable security foundation than direct provider protocols plus externally controlled state/merge authority.

CAO remains useful as a **provider/backend separation reference**, especially where its code distinguishes terminal process management from provider-specific behavior. Its Apache-2.0 license is straightforward for study and reuse. citeturn530342search4turn530342search5

Two distinctions deserve emphasis.

First, **Antigravity CLI is not Gemini CLI**. Agetor has separate harness rows and separate binaries for `agy` and `gemini`, with different continuation identifiers. The current Google Antigravity documentation describes `agy` as the Antigravity CLI using the shared Antigravity harness/authentication layer. A Gemini CLI integration should not be presented as Antigravity support. citeturn971197search1turn718889search1

Second, same-provider session resumption is **not cross-provider continuation**. AO's own handoff design is careful about this boundary; it only preserves a native conversation where the two interfaces are proven to name the same provider conversation. A Claude session cannot be safely “resumed” by passing an ID to Codex or Antigravity. Cross-provider replacement must be a new provider-native conversation that receives controller-owned task state, workspace state and evidence. citeturn971197search2

The official Antigravity headless permission behavior also changes how success must be measured. Because a permission-denied command may be soft-denied while the overall headless process exits `0`, a controller that equates process exit zero with task success would be unsound. It must consume result/status events and independently run the acceptance checks. citeturn718889search0

The major interface mismatch is **state ownership**. AO wants SQLite to be authoritative for sessions; Tower Crane wants `.tower-crane/*.json` plus `events.jsonl`; tasks.md can use a Git ref as its claim/event authority; coord owns its own SQLite database. Running all four unchanged would produce a distributed system of truth on a laptop. That would make crash recovery harder, not easier. The reusable value is in their **mechanisms**, not in preserving all of their storage boundaries. citeturn971197search3turn971197search0turn375168search6turn530342search1

Another mismatch is the meaning of “ownership.” AO's controller generation fences stale **controller events** inside one session. tasks.md's `claim_id` fences stale **task completion/release**. Neither alone prevents a process that still owns filesystem permissions from writing to an old worktree. A production controller needs both: controller/event fencing *and* a task ownership generation that is checked at submission/merge, coupled with termination or access revocation for the superseded worker. citeturn971197search2turn375168search6

The enforcement hierarchy that follows from these failures is important. A prompt such as “do not alter architecture” is an **instruction** and can be ignored. A read-only path mount or missing credential is a **capability restriction** and prevents a class of writes. A claim-generation check at submission is an **authorization fence** and prevents stale work from being accepted. A protected integration credential under controller ownership prevents the worker from merging itself. A test or static rule is a **mechanical acceptance check** but only for properties it actually measures. An independent model/human review can assess semantic requirements but is probabilistic and should not be described as a guarantee.
